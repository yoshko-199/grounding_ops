# Requirements for the next specification version

**Status: proposal, with one item adopted.** R10 is adopted in
[specification v0.6](../claim-verification-engine.v0.6.md). Everything else
here is still a proposal for a later version, and every behaviour described
as "today" is what the current code does. This document collects
what the [ten supplied claims](../../validation-ten-claims.md) and the
[demo pack](../../how-to/try-the-demo-pack.md) exposed, in two groups:

- **Requirements (R1–R8).** Things v0.5 does not cover. Closing any of them
  is a specification change, and should come with a version bump and the
  acceptance criteria that would fail without it. R1 is built, as pack
  interface v1.6.
- **Requirement R10, adopted in v0.6.** Rounded counts under §9.2. Built,
  with AC-13 v1.4 and pack interface v1.9.
- **Requirement R9, already built.** A plain-language bottom line above
  each result. v0.5 permits it, and it is in the code now; the spec should
  name it so that its constraints can fail a build.
- **Divergences (D1–D3), all fixed.** Places where the code did not do what
  v0.5 already says. These were defects, not new requirements. By the
  repository's own rule, when behaviour and specification disagree, one of
  them is wrong. Here it was the behaviour, and each was fixed without a
  version bump. They stay listed so the evidence and the fix stay together.

Each entry gives the evidence, what should be required, a suggested
approach, the criteria it touches, and the main risk.

---

## Requirements

### R1. Units

**Evidence.** Claim 1: "Water boils at 100 degrees Celsius (212 degrees
Fahrenheit)". The number pattern reads no unit beyond `%`, `percent` and
`points`, so "212" is compared against a series published in Celsius and
comes back *contradicted*. The claim is then *Substantially inaccurate*
for giving the same fact in a second unit.

**Requirement.** A quantity element carries the unit the claim states, and
a comparison happens only between a claim and a figure in the same unit.

**Suggestion.**
- Declare each measure's unit, and the phrases that name it, in the pack
  lexicon, so the vocabulary stays data rather than code.
- Never convert units in the engine. A conversion is a figure nobody
  retrieved. Compare only when the custodian publishes the figure in the
  claim's unit.
- On a unit mismatch, mark the element *unverified*, with the reason "the
  custodian publishes this measure in a different unit". Never mark it
  *contradicted*.

**Touches.** AC-7 (no computed figures), AC-13 (tolerance determinism),
AC-18 (element anchoring now spans number plus unit).

**Risk.** Unit phrases are language-specific, and a wrong unit reading
would contradict a true claim. Failing towards *unverified* keeps the
error on the safe side.

**Built, as pack interface v1.6.** Each lexicon declares `unit_phrases`
(unit id → phrases), required and allowed to be empty. A declared phrase
after a numeral joins the quantity element, so claim 1's second figure is
the element "212 degrees Fahrenheit". Before banding, an element whose unit
differs from its measure's is *unverified*, with a fixed reason, and is
never compared or converted. Claim 1 is now *Indeterminate*: "100 degrees
Celsius" verifies and the Fahrenheit figure is recorded as not compared.
The bottom line says so in plain words. The same change fixed a latent
reading in the old hardcoded pattern, which took "percentage points" as
"percent": a claim that the rate "fell 0.3 percentage points" had its
change compared against the rate's level and came back contradicted.
Tested in AC-13 (a figure in another unit is never banded), AC-18 (the
element spans its unit), the loader's checks, and the matcher's edge cases.
A unit stated *before* the figure ("£5", "USD 5") is read too, since pack
interface v1.7's `unit_prefixes`: the figure is compared only if every unit
stated around it is the measure's. Scale words ("£5bn", "5 billion") are read
since v1.8's `scale_words`, with an optional `published_scale` per measure for
series published in thousands or millions; both sides are scaled by exact
powers of ten, internally only. Still open: no pack in the tree yet publishes
a measure in a currency. A discrete count stated with a scale word was held
to §9.2's exact match, so "29 thousand" against a published count of
`28,700` was contradicted; spec v0.6 settles that ([R10](#r10-rounded-counts)).

### R2. Event dates

**Evidence.** Claim 4: "King John of England signed the Magna Carta in
1225". A year is always decomposed as a time period, which scopes a
comparison and is never compared itself. So a claim about *when something
happened* can only be reached or not reached; it can never be
contradicted.

**Requirement.** A claim that dates an event is checkable against a
custodian's register of events.

**Suggestion.**
- Add a new element kind, `event_date`, used only when the bound measure is
  declared in the pack as an event register (a new measure flag).
- Everywhere else a year stays a time period, exactly as today, so no
  existing claim changes behaviour.
- Match exactly, like a discrete count. The measure's known confusions
  carry the difference between an event and its later repetitions, such as
  a first sealing against its reissues.

**Touches.** AC-13 (discrete exact match), AC-18, and the pack interface
(a new measure field).

**Risk.** Deciding which verb makes a year an event date is lexical, and
it belongs in the pack vocabulary, not in the engine.

### R3. Active-voice causal verbs

**Evidence.** Claim 6: "Vaccines cause autism in children" derives
nothing. Every causal trigger ("due to", "caused by") puts the effect
first. In "A causes B" the cause comes first, so adding "cause" as a
trigger would state the relationship backwards.

**Requirement.** Causal derivation states the relationship in the
direction the claim asserts, whatever the voice.

**Suggestion.**
- Give each causal trigger a declared direction in the lexicon: effect
  first for "due to", cause first for "causes" and "leads to".
- The operation stays `causal-discharge`, since §9.7.2's list is about
  operations, not vocabulary, and the flank logic reads the direction.

**Touches.** §9.7.2 and AC-16 (anchoring and closure).

**Risk.** Directional vocabulary is easy to get backwards. Each trigger
needs a test that pins the direction of the statement it produces.

### R4. Compound claims

**Evidence.** Claim 10 joins two assertions with "and". Its comparative
derivation spans both ("…has been cut by is asserted to be more than half
since 1991"), and its first assertion leaves no trace at all (see R8).

**Requirement.** §6.2 already says: "Compound claims receive one verdict
per atomic assertion". The decomposition should split at a top-level
conjunction joining two independent clauses, and verify each.

**Suggestion.**
- Split only where each side has its own subject and verb, so that "rose
  and fell" is not split.
- The artifact carries one verdict per assertion and an optional overall
  read, each assertion with its own ledger. §7.1 applies to each.

**Touches.** AC-1 (every reconstruction with its ledger), AC-15 (a
reconstruction per assertion), and AC-18.

**Risk.** Mis-splitting produces two claims the claimant never made
separately. The split must be anchored and visible, never silent.

### R5. Classification facts

**Evidence.** Claim 3: "Humans are classified as mammals." It has no
quantity, so it is out of scope. Yet it is the kind of fact an
authoritative register does settle.

**Requirement: decide, either way.** Should §2 admit register-backed
administrative facts (a classification, a registration, a legal status),
checked for membership in a custodian's register?

**Arguments.**
- *For:* the engine already has an `administrative` element kind, and a
  register is a custodian of record in exactly §4's sense.
- *Against:* membership claims invite "is X a Y" questions whose
  definitions are contested, such as "is this group a terrorist
  organisation". The system's safety comes from narrowness, and every
  widening should earn its place.

### R6. Level claims and *Accurate*

**Evidence.** Claim 1v ("Water boils at 100 degrees Celsius at sea
level") verifies, and is capped at *Indeterminate*, because the robustness
sweep needs a direction to test. Today no level claim can be *Accurate*.

**Requirement: decide, either way.** Either record this cap as intended,
since §9.3's sweep exists to test a conclusion and a bare level asserts
none, or define what the sweep means for a level. For example, the
level's position in the range of recent revisions.

**Risk.** A level sweep that always holds would make *Accurate* cheap.
Any definition should be able to flip.

### R7. Series that aren't monthly

**Evidence.** The demo's annual murder-rate series could declare no
windows at all. The sweep counts windows in observations assuming monthly
data (`12m` is twelve observations, and `1y` is also twelve), and anchors
`prior_year` thirteen observations back.

**Requirement.** Windows and the `prior_year` baseline are computed from
the measure's declared cadence.

**Suggestion.** Declare a cadence per measure, or read it from its
custodian, and convert window names to observation counts from it. Refuse
a window the cadence cannot express, rather than guessing.

**Touches.** AC-11 (sweep coverage).

### R8. Text that becomes no element

**Evidence.** In claim 10, "gun violence is alien to most people's
experiences" matched no pattern, so it produced no element. It is in
neither the reconstruction nor the discard ledger, and the ledger says
"Nothing was discarded".

**Requirement.** Every span of the claim is accounted for: as an element,
as a discarded element, or listed as not examined.

**Suggestion.** After decomposition, compute the spans no element covers
and list them in the ledger as *not examined*, with the reason "no
element of the claim matched this text". Leave out connectives and
stopwords.

**Touches.** AC-1 (the ledger's completeness), AC-18.

**Risk.** A noisy ledger. The listing should skip spans that are only
function words.

### R10. Rounded counts

**Adopted in [v0.6](../claim-verification-engine.v0.6.md#0a-what-changed-in-v06).**
A count is an exact match at the precision the claim states; an exact half
rounds to either neighbour for every measure; approximation words the pack
declares ("about", "roughly") widen the stated precision to the last non-zero
digit; and there is no floor. "29 thousand" and "about 29,000" against a
published `28,700` are Verified, tagged `rounded`, and "29,000" written in
full is still held to exact match. Tested in AC-13; each rule
negative-checked.

**Evidence.** Since interface v1.8 reads scale words, "registered
job-seekers were 29 thousand" is read as a count stated to the nearest
thousand. §9.2 still gives discrete counts an exact match, so against a
published `28,700` the claim is Contradicted, and the claim is *False*. A
continuous figure stated at a coarser precision gets Band A's rounding
reading; a count never does. Separately, §9.2 does not say which way an
exact half rounds, and the code rounds half to even, choosing a convention
for the claimant.

**Requirement and draft text.** A count stated with a scale word is judged
at the precision it states, and a count written in full stays an exact
match. Drafted in full, with proposed §9.2 and AC-13 wording, worked
examples, alternatives and open questions:
[judge a rounded count at the precision it was stated in](9.2-rounded-counts.md).

**Touches.** AC-13 (rewritten), AC-3 (the precision is read from the claim,
not chosen).

**Risk.** A coarsely stated count verifies easily. The `rounded` tag and
the cited published count show the reader the exact figure.

### R9. A plain-language bottom line

**Evidence.** A reader asked for a short, plain answer above the full
record: what is true, what is false, the closest version the sources
support, and which sources. The full artifact answers all four, but spread
across a ledger of reasons, a flip table and a citation trail written for
an auditor.

**Today.** Built, within v0.5's constraints. Every result opens with a
*bottom line* section in `render()`, `render_html()`, `to_dict()` and the
stored read-back, written by `engine/render/bottom_line.py`. What it says,
and why, is in the [overview](../../overview.md#the-bottom-line). It follows
the working order of an empirical check: isolate the checkable assertion,
name the evidence that would settle it, go to the primary source, look for
disconfirming comparisons, and give a calibrated, provisional verdict.

**Requirement.** Add it to §7 as a named output section, with three
constraints the code already meets:
- It states every element the ledger removes, beside the closest verified
  version, so it is no more detachable than the reconstruction (§7.1).
- It has no length budget and is never emitted on its own (§7.2). It is
  the same record in plainer words, not a shorter record.
- It carries no numeral that is not the claimant's own or tied to a
  retrieval, and states no counts (§3).

**Touches.** AC-1, AC-2, AC-5 and AC-7 now each carry a test for it. A spec
section would let those tests cite a clause rather than an inference.

**Risk.** Plain words can overstate. The wording for each label is fixed in
code, reviewed like any other output, and never says "false" of a claim the
record did not contradict. Insufficient Data is stated as "neither confirmed
nor refuted", never as suspicion.

## Divergences from v0.5, all fixed without a version bump

### D1. Contested by definition folds into Insufficient Data

**v0.5 says** (§6.1): *Contested by definition* means "two authoritative
custodians differ because they measure different things. Both reported,
with the definitional gap explained". And §6.2 makes a definitionally
contested claim *Indeterminate*.

**The code does this instead** (claim 8, "the density of steel"): binding
finds both measures and names them. The verdict is then *Insufficient
Data*, the element is *unverified* ("no measure was bound"), and neither
custodian's figure is retrieved or shown.

**Suggested fix.** On a contested binding:
- retrieve each contested measure;
- mark the element *contested by definition*;
- cite both figures, with their known confusions as the definitional gap;
- let `claim_verdict` return *Indeterminate*, which it already does for
  contested elements.

This needs AC-4 and AC-14 tests showing that both figures are reported.

**Fixed.** `engine/pipeline.py` now pulls every contested measure whose
custodian has an adapter. Its in-scope elements are *contested by
definition*, every figure is cited, and each measure gets a routing note
naming the others as its alternatives. The verdict is *Indeterminate*.
Where no contested custodian can be reached, the elements are
*unreachable*, never *unverified*, and the verdict stays Insufficient
Data. Tested in `test_ac04.py` (both figures reported, rendered and linked)
and `test_ac14.py` (the unreachable case).

### D2. The band B `rounded` tag is never shown

**v0.5 says** (§9.2): "The `rounded` tag on Band B surfaces in output."

**The code does this instead:** `tolerance.py` computes the tag, and the
store records `tolerance_band = "B"`. But no output shows it. In claim 8v,
7700 against a published 7810 is verified, and the reader never learns it
was only verified to within rounding.

**Suggested fix.** Render verified elements with their band in the
reconstruction's citation, or in a short "verified elements" list beside
the ledger. This needs an AC-13 test asserting that the tag appears in
`render()`, `render_html()` and `to_dict()`.

**Fixed.** The artifact carries the fragments verified in band B. Every
output says "Verified to within rounding, not exactly", quoting the
claimant's figure, and `to_dict()` has a `rounded` key. The bottom line says
the same in its *True* line, beside the published figure. Tested in
`test_ac13.py`, including that an exact match carries no tag.

### D3. `last_break` is anchored at the middle of the series

**v0.5 says** (§9.3, with §9.5): the `last_break` baseline compares
against the most recent declared series break.

**The code does this instead:** `sweep._baseline_sweep` anchors
`last_break` at `retrievals[len(retrievals) // 2]`, the middle of the
series, whatever breaks the pack declares. The first version of the demo's
*Misleading* verdict rested on exactly that phantom anchor, and was
redesigned so that it doesn't.

**Suggested fix.** Anchor at the latest declared break inside the
retrieved span, and skip the baseline, with no row, when there is none.
This needs an AC-11 test with a series that has no break inside it.

**Fixed.** `sweep._last_break_anchor` anchors at the first observation on or
after the latest declared break inside the retrieved span, and the sweep
emits no `last_break` row when no declared break falls inside it. The worked
example stays *Misleading*, and its phantom `last_break` row is gone. Tested
in `test_ac11.py` with a series whose midpoint and anchor differ, so the
test cannot pass by coincidence.
